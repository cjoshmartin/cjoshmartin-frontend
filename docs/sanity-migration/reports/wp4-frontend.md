# WP4: Next.js frontend on Sanity

The Next.js app (branch `sanity-migration`) now reads every page from Sanity project `j3vdh6ti`
instead of the Wagtail API. Visual Editing (Presentation tool, Draft Mode, `defineLive`) is wired
in, every bug in plan §7.3 is fixed, and the Wagtail fetch layer is gone. `npm run lint`,
`npm run typecheck` and `npm run build` pass, and a production build reading the `production`
dataset passed a 54-check smoke test of every route.

Detailed logs (outside git): `~/cjoshmartin-migration/reports/wp4/` (smoke test, draft-mode test,
browser checks, parity JSON, page-height comparison, and the scripts that produced them).

## Decisions and deviations

1. **Developer audience filter kept.** The live `/projects` page and the home previews only show
   `DEV` projects (the old code passed `project_audience=DEV` to the Wagtail API). Plan §6 doesn't
   mention it; the queries keep it so the output matches. Maker projects (Squid Games Nerf Gun,
   ...) open by URL and appear on `/screen`, as today.
2. **`@mux/mux-video-react` instead of `@mux/mux-player-react`** (the brief allows either). It renders
   a plain `<video>` with native controls, so the markup and look are the same as the old
   `<video autoPlay loop playsInline controls muted>`. Props: `autoPlay="muted" muted loop
   playsInline controls streamType="on-demand"`. Checked in Chromium: all rendered videos play,
   muted, looping, inline, with controls.
3. **Real 404 needs the proxy.** The root layout wraps pages in `<Suspense>` (the loader), so a
   page's `notFound()` happens after streaming started and can only produce a soft 404 (status 200
   + `noindex`, which is what the live site does today). `proxy.ts` checks
   `/blog/:slug`, `/projects/:slug`, `/flex/:slug` against published documents (API CDN, no token)
   and rewrites unknown slugs to an unmatched path, which renders the not-found page with status
   404. It skips the check in Draft Mode (drafts can have any slug) and lets the page decide if
   Sanity can't be reached (logged).
4. **Flex pages get their own metadata** (`<title>` "Portfolio - Josh Martin's Website" and a
   canonical `https://cjoshmartin.com/flex/<slug>`). Before, they inherited the home page's title
   and canonical. The description still falls back to the site default.
5. **og:image** is a 1200×630 hotspot crop from `cdn.sanity.io` as JPEG (Sanity's advice for
   crawlers), instead of the full-size original.
6. **Descriptions changed on 2 posts** (`bluetooth-low-energy-…`, `creating-zip-files-…`): they have
   a Wagtail search description (now `seo.description`), which bug fix 2 now uses.
7. **Ordering** uses `date desc`, ties broken by `legacy.wagtailId asc` (Wagtail tree order). Same
   order as the live `/blog`, `/projects` and previews (checked).
8. **Read time** counts words properly across blocks (the old regex glued adjacent paragraphs).
   The minute values are identical for all 20 posts and projects (checked).
9. **Videos without a Mux asset render nothing** and log
   `PortableTextBody: video block <key> has no playable Mux asset` on the server. Both datasets
   have 10 `mux.videoAsset` documents (Mux free plan); 19 video blocks reference the missing ones
   (project-6: 3, project-23: 10, blogPost-19: 3, blogPost-39: 3). They play once WP3 reruns the
   Mux step on a paid plan; no frontend change is needed.
10. **STL files load from `cdn.sanity.io/files`**, which only sends CORS headers to the project's
    CORS origins (localhost:3000/3333, cjoshmartin.com, www, the scoped Vercel previews). A failed
    load used to crash the whole page ("This page couldn't load"); `STLErrorBoundary.tsx` now
    logs it and shows "(the 3D model could not be loaded)". The STL `scale` field is stored but,
    as before, not used by the viewer.
11. **YouTube iframe `title`** is "YouTube video player" (the oEmbed video title isn't stored).
12. **`/portfolio` and `/info`** are unchanged (page-level `redirect()`, which streams as a
    client-side refresh to `/projects` and `/`, as on the live site).
13. **Sitemap `lastmod`** is `_updatedAt`, which is the import time (2026-11-25) for every
    migrated document until it is edited.

### Decisions

1. **A `<source>` with a type, not `<video src>`.** The brief asks for `type="video/mp4"`, and that
   attribute only exists on `<source>`. The type is set only when the asset's `mimeType` is
   `video/mp4`. A block that is not converted yet, or whose conversion failed, still plays its
   current file, without a type. Reason: Chromium skips a source typed `video/quicktime` without
   trying it, but plays an untyped `.mov` it can decode (shown with the fixtures below).
2. **`key={url}` on the `<video>`.** Changing a `<source>` `src` does not reload a media element.
   When the converter switches `file` to the MP4, SanityLive re-renders the page. The new key makes
   React mount a fresh element, which loads the MP4.
3. **A fallback link inside `<video>`** (`Download <filename>`), as the Next.js video guide
   (`node_modules/next/dist/docs/01-app/02-guides/videos.md`) recommends. Browsers that support
   video never show it, so nothing on the page changes. It is the only use of `filename`.
4. **No conversion-status logic on the page.** The page plays whatever `file` points to. Status is
   the Studio's concern (the block preview and a validation warning).
5. **TypeGen without rewriting `studio/schema.json`.** `npm run typegen` in `studio/` starts by
   re-extracting `studio/schema.json`, which this package does not own. Instead, the schema was
   extracted to a temp path, which matched `studio/schema.json` byte for byte. Then
   `npx sanity typegen generate` ran in `studio/` (the second half of the same script). The output
   is the same as `npm run typegen`'s.
6. **Comparison with the old site.** The live Wagtail-fed site renders
   `<video src=".../images-for-cms/media/<file>.mov" autoPlay="" loop="" playsInline="" controls="" muted="">`.
   The new markup has the same attributes plus `preload="metadata"`. The file is the MP4 at
   `cdn.sanity.io/files/j3vdh6ti/<dataset>/`, which answers range requests (`206`, `accept-ranges: bytes`).
   `app/globals.css` still styles `video` (block, full width, at most 550 px high). React 19.2
   server-renders `muted=""`, so the server HTML can autoplay before hydration.

1. **Medium (WP4 design, not changed here): content published while no browser has the site open

   - **How it works.** `defineLive`'s `sanityFetch` caches each query result with
     `revalidate: false` and Sanity sync tags. Only `<SanityLive>`'s server action expires those
     tags, and only when a browser that is connected at the moment of the change receives the live
     event. Nothing on `welcome` catches up on missed changes (`next-sanity` 13.5.1,
     `dist/SanityLive.js`).
   - **What happened here.** My first production run cached the pages before the data package
     rewrote the videos. After the rewrite, at 06:14:41 UTC, the same server kept serving cached
     responses dated 05:27:55, with no video URLs. The API and API CDN already returned the MP4s
     (`smoke-production-v2-stale-cache.log`).
   - **The fix used for this test.** Deleting the local `.next/cache/fetch-cache` and restarting
     the server fixed it at once.
   - **Risk.** The same can happen to any deployment whose Data Cache was filled before the rewrite
     (for example the `sanity-migration` Preview), and later to any editor change published while
     nobody is on the site.
   - **Options for the owner:**
     - purge the Vercel Data Cache after the data migration;
     - add tag revalidation from a Sanity webhook (Sanity's "Revalidate Next.js pages with Sanity
       webhooks" guide);
     - or add a time-based upper bound.
